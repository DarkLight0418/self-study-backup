## 0. 6장 전체 연결 공식

```text
클라우드 네이티브 모범 사례 =
기존 시스템의 한계
→ 작은 단위로 분리
→ 장애·보안·데이터·성능·운영 문제를 자동화/분산/격리로 해결
→ 안정적이고 확장 가능한 운영
```

```text
핵심 흐름:
모놀리스 분리
→ 회복력 확보
→ 보안 강화
→ 데이터 분산 관리
→ 성능/확장성 확보
→ 함수/운용/로깅/통신/컨테이너 모범 사례 적용
```

```text
서술형 답안 공식:
문제: 복잡한 모놀리스, 장애 전파, 보안 위험, 데이터 병목, 운영 복잡성
해결: 서비스 분리, Retry/Circuit Breaker/Bulkhead, 최소 권한, 파티셔닝, CI/CD, Observability
효과: 빠른 배포, 장애 격리, 보안 강화, 확장성 향상, 운영 안정성
```

## 1. 클라우드 네이티브로 이동하기

```text
목표 = 모놀리스를 한 번에 갈아엎지 않고 점진적으로 클라우드 네이티브화
```

### 왜 이동하는가?

```text
코드베이스가 커짐
→ 업데이트 출시가 오래 걸림
→ 구성 요소별 요구 규모가 다름
→ 독립 확장/배포 필요
```

- 단순히 클라우드로 옮기기만 하면 IaaS 사용에 가까움
- 클라우드 네이티브는 애플리케이션 구조 자체를 재설계
- 프런트엔드/비즈니스/데이터 계층을 독립적으로 확장 가능하게 함

### 이동 전략

```text
단순한 서비스 먼저 분리
→ 작은 규모에서 운영 학습
→ CI/CD와 자동화 경험 축적
→ 점진적 마이그레이션
```

### 손상 방지 레이어, ACL

```text
ACL = Anticorruption Layer
= 기존 모놀리스와 새 서비스 사이의 번역 계층
```

- 역할: 파사드/어댑터
- 기능: 프로토콜, 스키마, 요청/응답 변환
- 효과: 기존 시스템의 구조가 새 서비스에 오염되는 것 방지

```text
모놀리스 → [ACL: 요청/응답 변환] → 새 서비스
```

### 스트랭글러 패턴

```text
Strangler Pattern =
모놀리스를 한 번에 제거하지 않고,
게이트웨이를 통해 새 서비스/함수로 트래픽을 점진적으로 이동
```

```text
처음: 모든 요청 → 모놀리스
중간: 일부 요청 → 새 서비스/함수
마지막: 대부분 요청 → 새 서비스, 모놀리스 제거
```

### 데이터 마이그레이션

```text
중앙 공유 DB 분해
→ 신규 DB와 기존 DB 공존
→ 새 서비스로 트래픽 전환
→ 기존 DB/모놀리스 점진 제거
```

### 서술형 연결 문장

```text
모놀리스를 클라우드 네이티브로 전환할 때는 전체 시스템을 한 번에 교체하면 위험하다.
따라서 의존성이 적은 기능부터 분리하고, ACL로 기존 시스템과 새 서비스를 연결하며,
Strangler 패턴으로 트래픽을 점진적으로 이전한다.
이 방식은 장애 위험을 줄이고, 서비스별 독립 배포와 확장을 가능하게 한다.
```

## 2. 회복력 확인

```text
회복력 = 장애 발생 시 다운타임과 데이터 유실을 줄이는 능력
```

### 기본 관점

```text
장애는 안 나는 것이 아니라, 항상 발생한다고 가정해야 함
```

### Retry

```text
Retry = 일시적 실패를 다시 시도하여 복구
```

| 전략 | 의미 | 주의 |
|---|---|---|
| 상수 재시도 | 매번 같은 시간 대기 | 단순하지만 부하 가능 |
| 선형 재시도 | 대기 시간을 일정하게 증가 | 점진적 완화 |
| 지수 백오프 | 대기 시간을 지수적으로 증가 | 가장 안전한 편 |
| 횟수 제한 | 지정 횟수 후 중단 | 무한 재시도 방지 |

```text
주의: 무제한 재시도 → 시스템 부하 증가 → 장애 확대
```

### Circuit Breaker

```text
Circuit Breaker = 실패가 일정 수 이상이면 일정 시간 동안 요청 차단
```

- 목적: 일시적 실패가 아닌 장애에서 전체 시스템 보호
- 효과: 장애 전파 방지, 빠른 실패 반환

### Graceful Degradation

```text
우아한 성능 저하 =
장애 중에도 최소한의 사용자 경험 제공
```

- 예: DB 검색 불가 → 캐시 데이터 표시
- 복구 후 최신 데이터 표시

### Bulkhead

```text
Bulkhead = 시스템을 독립된 구역으로 나누어 장애 격리
```

- 정상 부분과 장애 부분 분리
- 한 서비스 장애가 전체 장애로 번지는 것 방지

### Health / Liveness / Readiness

| 구분 | 의미 |
|---|---|
| Health Check | 서비스 정상 작동 여부 확인 |
| Liveness Probe | 컨테이너 재시작 여부 결정 |
| Readiness Probe | 파드가 트래픽 받을 준비가 되었는지 결정 |

### Rate Limiting / Throttling

| 구분 | 의미 |
|---|---|
| Rate Limiting | 들어오는 요청 개수 제한 |
| Throttling | 나가는 요청 개수 제한 |

### 서술형 연결 문장

```text
클라우드 네이티브 시스템은 분산 구조이므로 장애가 일부 서비스에서 전체 시스템으로 전파될 수 있다.
Retry는 일시적 장애를 처리하고, Circuit Breaker는 반복 실패 시 요청을 차단하며,
Bulkhead는 장애 영역을 격리한다.
또한 Liveness와 Readiness Probe를 통해 컨테이너 재시작과 트래픽 수신 가능 여부를 판단하여 운영 안정성을 높인다.
```

## 3. 보안 강화

```text
보안 = 나중에 추가하는 기능이 아니라 설계 단계부터 포함해야 하는 요구사항
```

### 핵심 원칙

```text
보안 요구사항도 기능 요구사항과 동일하게 취급
설계 시 보안 통합
접근 권한은 최소한만 부여
환경/계정/테넌트 분리
```

### 최소 권한 원칙

```text
필요한 권한만 부여
예: 읽기만 필요하면 쓰기 권한 금지
```

### 비밀정보 관리

```text
비밀번호/API 키/인증서
→ 코드나 이미지에 저장 금지
→ Secret, 암호화 저장소, 관리형 보안 솔루션 사용
```

### 데이터 보호

| 상황 | 해결 |
|---|---|
| 저장 데이터 | 암호화, 난독화 |
| 통신 데이터 | TLS/HTTPS |
| 인증/권한 | 연합 ID 관리, RBAC |
| 파드 간 접근 | Kubernetes Network Policy |

### RBAC

```text
RBAC = Role-Based Access Control
= 역할 기반 접근 제어
```

- 사용자/서비스별 필요한 자원만 접근 허용
- 심층 방어 전략에 활용

### 파드 격리

```text
Network Policy로 허용하지 않은 연결 차단
→ 서비스 간 불필요한 접근 방지
```

### 서술형 연결 문장

```text
클라우드 네이티브 환경은 여러 서비스와 클러스터 자원이 연결되어 있어 보안 범위가 넓다.
따라서 최소 권한 원칙, Secret 기반 비밀정보 관리, TLS 통신 암호화, RBAC, 네트워크 정책을 적용해야 한다.
이는 침해 범위를 줄이고 서비스 간 불필요한 접근을 차단하여 전체 시스템 보안을 강화한다.
```

## 4. 데이터 다루기

```text
데이터 설계 = 서비스 확장성, 가용성, 비용을 좌우하는 핵심
```

### 관리형 데이터베이스

```text
관리형 DB/분석 서비스 사용
→ DB 배포·관리 부담 감소
→ 운영 비용과 장애 대응 부담 완화
```

### 데이터스토어 선택

```text
데이터 타입 / 읽기 요구 / 쓰기 요구에 맞는 저장소 선택
```

- 모든 데이터를 하나의 DB에 넣지 않음
- 서비스 요구에 맞는 여러 종류의 데이터스토어 사용 가능

### 고가용성과 확장

```text
여러 리전/존에 데이터 보관
→ 장애 복구 가능
→ 가용성 향상
```

```text
파티셔닝 / 복제
→ DB 분산
→ 스케일아웃 가능
```

### I/O 최적화

| 문제 | 해결 |
|---|---|
| Overfetching | 필요한 데이터만 가져오기 |
| Chatty I/O | 작고 잦은 요청 줄이기 |
| DB에 비즈니스 로직 집중 | DB와 비즈니스 로직 분리 |
| 실제와 다른 테스트 데이터 | 실서비스와 유사한 데이터로 테스트 |

### 일시적 장애 처리

```text
DB 장애도 항상 발생한다고 가정
→ 일시적 장애 처리 라이브러리 사용
→ Retry, Backoff, Circuit Breaker와 연결
```

### 서술형 연결 문장

```text
클라우드 네이티브 환경에서는 데이터가 성능과 확장성의 병목이 되기 쉽다.
따라서 요구사항에 맞는 데이터스토어를 선택하고, 여러 리전과 존에 데이터를 분산하며,
파티셔닝과 복제를 통해 스케일아웃을 지원해야 한다.
또한 오버페칭과 chatty I/O를 줄여 불필요한 네트워크 및 DB 부하를 완화할 수 있다.
```

## 5. 성능과 확장성

```text
성능 = 특정 시간 동안 작업을 얼마나 처리하는가
확장성 = 성능 저하 없이 부하 증가를 처리하는 능력
```

### 핵심 설계

```text
상태 없는 서비스 설계
→ 스케일업보다 스케일아웃 가능
→ 가용성에 영향 없이 부하 처리
```

### Auto Scaling

| 구분 | 의미 |
|---|---|
| HPA | CPU, 메모리, 커스텀 메트릭 기반 파드 수 조절 |
| Cluster Autoscaling | 파드 스케일이 불가능하면 노드 수 조절 |

### 캐시

```text
자주 사용하는 데이터 캐싱
→ 응답 속도 향상
→ DB 부하 감소
```

### 파티셔닝

```text
서비스 한계를 넘기 위해 작업을 여러 인스턴스로 분산
```

### 서술형 연결 문장

```text
성능은 현재 처리 능력이고, 확장성은 부하 증가에도 성능을 유지하는 능력이다.
클라우드 네이티브에서는 상태 없는 서비스를 설계하여 수평 확장이 가능하게 하고,
Kubernetes HPA와 클러스터 오토스케일링을 활용해 부하 변화에 대응한다.
또한 캐시와 파티셔닝을 통해 DB와 서비스 병목을 줄일 수 있다.
```

## 6. 함수

```text
함수 = 작고, 단순하고, 상태 없는 단일 작업 단위
```

### 함수 설계 원칙

```text
단일 목적
가벼움
상태 없음
실행 시간 짧게
함수 로직과 진입 지점 분리
```

### 함수 연계 주의

```text
함수가 다른 함수를 직접 호출하는 구조 지양
→ 큐나 데이터스토어 이벤트로 간접 구동
```

### 왜 단순해야 하는가?

```text
단일 책임 원칙
→ 이해 쉬움
→ 테스트/디버깅 쉬움
→ FaaS 실행 시간 제약 대응
```

### Queue 기반 연결

```text
함수 A → Queue/Data Store → 이벤트 발생 → 함수 B 실행
```

- 직접 호출보다 결합도 낮음
- 장애 격리와 확장성에 유리

### 서술형 연결 문장

```text
서버리스 함수는 실행 시간이 제한되고 이벤트 기반으로 동작하므로 작고 단순하게 설계해야 한다.
함수는 단일 목적을 가져야 하며 상태를 내부에 저장하지 않아야 한다.
또한 함수 간 직접 호출 대신 큐를 사용하면 결합도를 낮추고 비동기 처리를 통해 확장성과 회복력을 높일 수 있다.
```

## 7. 운용

```text
운용 = 배포 이후 실제 서비스를 안정적으로 유지하기 위한 실천 방법
```

### 배포와 출시 구분

| 구분 | 의미 |
|---|---|
| 배포 | 빌드한 구성 요소를 환경에 넣어두는 행위 |
| 출시 | 배포한 구성 요소에 실제 트래픽을 배분하는 행위 |

```text
Deploy = 환경에 올림
Release = 사용자 트래픽 연결
```

### 운영 원칙

```text
작은 배포
제로 다운타임 출시
CI/CD 정의를 구성 요소와 함께 관리
인프라 직접 수정 금지
컨테이너화된 빌드
IaC
환경 격리
브랜치 전략
```

### 인프라 수정 금지

```text
운영 중인 인프라를 직접 수정하지 않음
→ 변경 추적 가능
→ 재배포로 일관성 유지
```

### Namespace / 환경 격리

```text
Namespace = Kubernetes 자원 그룹화
환경 격리 = 개발/스테이징/테스트/운영 분리
```

### 서술형 연결 문장

```text
운영 단계에서는 배포와 출시를 구분하는 것이 중요하다.
배포는 구성 요소를 환경에 올리는 것이고, 출시는 실제 트래픽을 배분하는 것이다.
작은 배포, 제로 다운타임 출시, IaC, 환경 격리, CI/CD 설정 관리를 적용하면 장애 위험을 줄이고 롤백과 추적이 쉬워진다.
```

```text
마이크로서비스 환경에서는 서비스가 독립적으로 배포되므로 하위/상위 호환성과 명확한 API 계약이 중요하다.
비동기 통신과 큐/스트림을 사용하면 트래픽 스파이크를 완충하고 서비스 간 결합도를 낮출 수 있다.
또한 효율적 직렬화, 일괄 처리, Claim Check 패턴을 활용하면 통신 비용과 자원 사용을 줄일 수 있다.
```

## 10. 컨테이너

## 11. 6장 핵심 비교표

| 비교 | A | B | 핵심 차이 |
|---|---|---|---|
| IaaS 이전 vs Cloud Native 재설계 | 인프라만 클라우드 | 앱 구조까지 재설계 | 단순 이전 vs 구조 개선 |
| ACL vs Strangler | 기존-신규 사이 번역 | 트래픽 점진 전환 | 변환 계층 vs 마이그레이션 방식 |
| Retry vs Circuit Breaker | 다시 시도 | 실패 시 차단 | 일시 장애 처리 vs 장애 확산 방지 |
| Liveness vs Readiness | 재시작 여부 | 트래픽 수신 여부 | 살아있나 vs 받을 준비 됐나 |
| Rate Limiting vs Throttling | 들어오는 요청 제한 | 나가는 요청 제한 | inbound vs outbound |
| 인증 vs 권한 | 누구인가 | 무엇을 할 수 있나 | identity vs permission |
| 성능 vs 확장성 | 현재 처리 능력 | 부하 증가 대응 | 처리량 vs 성장 대응 |
| Scale-up vs Scale-out | 자원 증설 | 인스턴스 증가 | 큰 서버 vs 여러 서버 |
| Deploy vs Release | 환경에 올림 | 트래픽 연결 | 배포 vs 출시 |
| Log vs Metric vs Trace | 사건 기록 | 수치 지표 | 요청 흐름 |
| Sync vs Async | 즉시 응답 의존 | 큐/이벤트 기반 | 강결합 vs 느슨한 결합 |
| Batch vs Claim Check | 묶어서 처리 | 큰 메시지 참조만 전달 | 처리 효율 vs 메시지 경량화 |
| Config/Secret in Image vs External Secret | 이미지 내부 저장 | 외부 주입 | 위험 vs 안전 |

## 12. 서술형 예상 문제 답안 뼈대

### Q1. 모놀리스를 클라우드 네이티브로 전환할 때 고려할 점

```text
모놀리스는 코드베이스가 커질수록 업데이트와 배포가 느려지고,
구성 요소별 확장 요구사항이 달라도 독립적으로 대응하기 어렵다.
따라서 의존성이 적은 서비스부터 분리하고,
ACL로 기존 시스템과 새 서비스 간 요청/응답을 변환하며,
Strangler 패턴으로 트래픽을 점진적으로 새 서비스로 이전해야 한다.
이를 통해 위험을 줄이면서 독립 배포와 확장성을 확보할 수 있다.
```

### Q2. 회복력을 높이기 위한 패턴을 설명하라

```text
클라우드 네이티브 시스템에서는 장애가 항상 발생한다고 가정해야 한다.
Retry는 일시적 실패를 다시 시도하여 복구하고,
Circuit Breaker는 반복 실패 시 요청을 차단하여 장애 전파를 막는다.
Bulkhead는 시스템을 독립 영역으로 나누어 일부 장애가 전체로 확산되는 것을 방지한다.
또한 Liveness와 Readiness Probe를 통해 컨테이너 재시작과 트래픽 수신 가능 여부를 판단한다.
```

### Q3. 클라우드 네이티브 보안 강화 방안을 설명하라

```text
보안은 배포 후 추가하는 기능이 아니라 설계 단계부터 포함되어야 한다.
최소 권한 원칙에 따라 필요한 권한만 부여하고,
Secret과 관리형 보안 솔루션을 사용하여 비밀정보를 코드나 이미지에 저장하지 않아야 한다.
또한 TLS로 통신을 암호화하고, RBAC와 네트워크 정책으로 서비스와 파드 간 접근을 제한해야 한다.
```

### Q4. 데이터 관리에서 확장성과 가용성을 높이는 방법

```text
데이터는 클라우드 네이티브 시스템에서 성능과 확장성의 병목이 되기 쉽다.
관리형 데이터베이스를 사용하면 운영 부담을 줄일 수 있고,
요구사항에 맞는 데이터스토어를 선택하면 비용과 성능을 최적화할 수 있다.
또한 데이터를 여러 리전과 존에 보관하고, 파티셔닝과 복제를 사용하면 장애 복구와 스케일아웃이 가능하다.
```

### Q5. 서비스 커뮤니케이션에서 비동기 통신과 큐가 중요한 이유

```text
마이크로서비스는 여러 서비스가 분산되어 실행되므로 동기 호출만 사용하면 장애와 지연이 전파될 수 있다.
비동기 통신과 큐/스트림을 사용하면 요청을 버퍼링하고 처리 능력에 맞게 소비할 수 있다.
이는 트래픽 스파이크를 완충하고 서비스 간 결합도를 낮추며, 가용성과 확장성을 높인다.
```

### Q6. 컨테이너 운영 시 주의할 점

```text
컨테이너 이미지는 신뢰할 수 있는 저장소에 보관하고 명시적 태그를 사용해야 한다.
이미지는 작게 유지하여 배포 속도와 보안을 개선하고, 취약점 검색 도구로 보안 위험을 줄여야 한다.
또한 privileged 모드를 피하고, 하나의 컨테이너에는 하나의 애플리케이션만 실행하는 것이 좋다.
컨테이너는 휘발성이 있으므로 데이터는 볼륨에 저장하고, 비밀정보는 이미지 내부가 아니라 Secret이나 외부 설정으로 제공해야 한다.
```

## 13. 6장 마지막 암기 문장

```text
모놀리스 전환은 한 번에 하지 말고 점진적으로 한다.
ACL은 기존 시스템과 새 서비스 사이의 번역 계층이다.
Strangler는 트래픽을 새 서비스로 점진적으로 옮기는 패턴이다.
Retry는 일시 장애, Circuit Breaker는 반복 장애, Bulkhead는 장애 격리다.
Liveness는 재시작 여부, Readiness는 트래픽 받을 준비 여부다.
보안은 설계 단계부터 포함하고, 권한은 최소한만 부여한다.
Config와 Secret은 코드/이미지에 넣지 말고 외부에서 주입한다.
성능은 처리 능력, 확장성은 부하 증가 대응 능력이다.
상태 없는 서비스가 스케일아웃에 유리하다.
Deploy는 환경에 올리는 것, Release는 트래픽을 연결하는 것이다.
CID는 분산 서비스 요청 흐름을 추적하는 ID다.
비동기 통신과 큐는 장애 전파와 트래픽 스파이크를 완화한다.
컨테이너는 작고 안전하게, 하나의 컨테이너에는 하나의 앱만 실행한다.
```
