## 1. 테스트 자동화

```text
테스트 자동화 = 빠른 배포와 출시 전 품질 보증의 전제
```

- 목적: 코드 변경 시 오류를 빠르게 발견
- 핵심: 작은 단위부터 자동 검증 → 문제 조기 발견 → 배포 위험 감소
- DevOps 연결: 자동 테스트가 있어야 CI/CD를 신뢰할 수 있음
- 효과: 품질 향상, 반복 검증 자동화, 빠른 피드백

### 테스트 피라미드

```text
Unit Test        : 빠름 / 많아야 함 / 메서드·클래스 단위
Service Test     : 서비스·컴포넌트 단위
Integration Test : 서비스 간 상호작용 검증
UI Test          : 느림 / 적게 / 사용자 화면·접근성 검증
```

```text
Unit 多 / 빠름 → Service → Integration → UI 少 / 느림
```

### 테스트 더블

| 구분 | 의미 | 핵심 |
|---|---|---|
| Mock | 객체 간 호출/상호작용 검증 | “제대로 호출됐나?” |
| Fake | 실제처럼 동작하는 가짜 구현 | “진짜 API 대신 사용” |
| Stub | 정해진 값만 반환 | “값만 흉내” |

### 주요 테스트 유형

| 테스트 | 핵심 목적 |
|---|---|
| 성능 테스트 | 응답 시간, 기능 단위 병목 확인 |
| 부하 테스트 | 최대/피크 트래픽, 장애 지점 확인 |
| 보안/침투 테스트 | 취약점, 불필요한 권한 탐지 |
| 스모크 테스트 | 핵심 기능이 살아있는지 빠르게 확인 |
| 카나리 테스트 | 소수 사용자에게 먼저 배포 후 검증 |
| A/B 테스트 | 두 버전의 트래픽/메트릭 비교 |
| 카오스 테스트 | 장애를 일부러 발생시켜 회복력 검증 |
| 퍼징 테스트 | 예상 밖 입력으로 취약점 탐색 |

### 테스트 실행 시점

```text
머지 전      = Unit Test
머지 전/후   = Service Test
머지 후      = Integration Test
배포 후      = Canary / A-B / Chaos
```

### 서술형 연결 문장

```text
테스트 자동화는 CI/CD의 신뢰성을 높인다.
코드 변경마다 자동 검증을 수행하면 오류를 조기에 발견할 수 있고,
운영 배포 전 위험을 줄여 빠른 배포와 품질 향상을 동시에 달성할 수 있다.
```

## 2. CI/CD

```text
CI/CD = 개발 → 빌드 → 테스트 → 배포를 자동화하는 DevOps 핵심 흐름
```

### CI

```text
CI = Continuous Integration
= 코드 변경마다 자동 빌드 + 자동 테스트
```

- 목적: 문제를 초기에 발견
- 효과: 통합 오류 감소, 빠른 피드백
- 도구: Jenkins, GitHub Actions, GitLab CI

### CD 구분

| 구분 | 의미 | 핵심 |
|---|---|---|
| Continuous Delivery | 언제든 배포 가능한 상태 유지 | 승인 후 배포 |
| Continuous Deployment | 운영 환경까지 자동 배포 | 자동 운영 배포 |

### 파이프라인 흐름

```text
Commit → Build → Test → Quality Check → Staging → Production
```

- Build: JAR, Docker Image 등 실행 가능한 형태로 패키징
- Test: Unit, Integration 등 자동 실행
- Quality Check: SonarQube, ESLint 등 코드 품질/보안 검사
- Staging: 운영 전 테스트 환경 배포
- Production: 실제 운영 환경 배포

### 장점

```text
배포 속도 향상 / 반복 작업 감소 / 테스트 자동화로 품질 향상 / 빠른 피드백
```

### 문제점과 해결안

| 문제 | 해결 |
|---|---|
| 수동 배포로 실수 발생 | CI/CD 파이프라인 자동화 |
| 환경 차이로 오류 발생 | Docker 이미지 기반 배포 |
| 장애를 늦게 발견 | 테스트 + 모니터링 연계 |
| 배포가 두려움 | 작은 변경을 자주 배포 |

### 서술형 연결 문장

```text
CI/CD는 배포 과정을 자동화하여 개발과 운영 사이의 지연을 줄인다.
특히 자동 테스트와 결합되면 잦은 코드 변경에도 품질을 유지할 수 있으며,
Docker와 Kubernetes를 함께 사용하면 환경 일관성과 무중단 배포까지 확보할 수 있다.
```

## 3. 개발 환경과 도구

```text
개발 환경 관리 = 로컬 개발 편의성과 클라우드 운영환경 일치를 동시에 추구
```

### 핵심 문제

```text
“내 PC에서는 잘 돼요.”
→ 로컬 환경과 운영 환경의 차이
→ 의존성, 설정, 네트워크, 클러스터 차이 발생
```

### 해결 방향

```text
컨테이너로 환경 통일
로컬에서 빠르게 테스트
클라우드/쿠버네티스 환경과 최대한 유사하게 개발
```

### 주요 도구

| 도구 | 핵심 |
|---|---|
| Docker Compose | 여러 컨테이너와 의존성을 로컬에서 함께 실행 |
| Minikube | 로컬 단일 노드 Kubernetes 실행 |
| Skaffold | 코드 변경 → 이미지 빌드 → K8s 배포 자동화 |
| Draft | K8s 배포 자동화 지원 |
| KSync | 원격 클러스터 컨테이너와 로컬 파일 동기화 |
| Telepresence | 로컬 컨테이너와 원격 K8s 클러스터 연결 |

### 서술형 연결 문장

```text
개발 환경과 운영 환경이 다르면 테스트 결과의 신뢰성이 떨어진다.
Docker Compose, Minikube, Skaffold 같은 도구를 사용하면
로컬 개발 환경을 클라우드 운영 환경과 유사하게 만들 수 있고,
이는 CI/CD 실패를 줄이고 배포 안정성을 높인다.
```

## 4. 모니터링과 관측성

```text
모니터링 = 시스템 상태 감시
관측성 = 왜, 어디서, 어떻게 문제가 생겼는지 추론하는 능력
```

### 왜 중요한가?

```text
장애가 발생했다는 사실만 아는 것은 부족함
→ 원인, 위치, 영향 범위를 파악해야 복구 가능
```

### 3요소

| 요소 | 의미 | 질문 |
|---|---|---|
| Log | 사건 기록 | 무슨 일이 있었나? |
| Metric | 수치 지표 | 얼마나 느려졌나/증가했나? |
| Trace | 요청 흐름 추적 | 어디서 지연·오류가 났나? |

### 목적

```text
장애 조기 감지 / 병목 지점 파악 / MTTR 감소 / 서비스 품질 관리 / SLO·SLA 관리
```

### 도구

```text
Prometheus / Grafana / ELK Stack / Datadog
```

### DevOps와 SRE 연결

| 구분 | DevOps | SRE |
|---|---|---|
| 성격 | 문화·철학 | 엔지니어링 역할 |
| 초점 | 협업·자동화 | 신뢰성·가용성 |
| 지표 | 배포 속도, 자동화 | SLA, SLO, MTTR |

### 서술형 연결 문장

```text
모니터링과 관측성은 운영 중인 시스템의 문제를 빠르게 발견하고 원인을 분석하기 위한 기반이다.
DevOps에서는 빠른 피드백 루프를 만들기 위해 필요하고,
SRE에서는 SLA/SLO를 만족시키기 위한 신뢰성 관리 수단으로 활용된다.
```

## 5. 설정 관리와 IaC

```text
설정 관리 = 코드와 설정을 분리하여 환경별 설정을 안전하게 관리
```

### 핵심 문제

```text
설정이 코드에 포함됨
→ 환경 변경 때 재빌드 필요
→ 비밀번호 노출 위험
→ 개발/운영 환경 차이 발생
```

### 해결 방향

```text
코드와 설정 분리
환경 변수/외부 설정 사용
민감 정보 별도 관리
인프라를 코드로 관리
```

### ConfigMap과 Secret

| 구분 | 용도 | 예시 |
|---|---|---|
| ConfigMap | 일반 설정 저장 | URL, 포트, 옵션 |
| Secret | 민감 정보 저장 | 비밀번호, 토큰, 인증키 |

```text
ConfigMap = 일반 설정
Secret = 민감 정보
```

### IaC

```text
IaC = Infrastructure as Code
= 서버·네트워크·보안 설정을 코드로 정의하고 관리
```

- 장점: 환경 재현 가능
- 장점: 설정 실수 감소
- 장점: 버전 관리 가능
- 도구: Terraform, Ansible, AWS CloudFormation

### 서술형 연결 문장

```text
설정 관리는 클라우드 네이티브 애플리케이션에서 코드와 환경 설정을 분리하기 위한 핵심 원칙이다.
ConfigMap과 Secret을 사용하면 환경별 설정과 민감 정보를 분리할 수 있고,
IaC를 사용하면 인프라 구성을 코드로 관리하여 재현성과 운영 일관성을 높일 수 있다.
```

## 6. 컨테이너와 DevOps 연결

```text
Docker = 포장
Kubernetes = 운영
DevOps = 빠르고 안정적인 전달 방식
```

### Docker

```text
앱 + 라이브러리 + 설정 + 실행환경
→ 하나의 이미지로 패키징
→ 어디서든 동일하게 실행
```

- 해결 문제: 환경 차이
- 효과: 배포 일관성, 테스트 신뢰성

### Kubernetes

```text
컨테이너 자동 배포·확장·복구·관리
```

- 선언형 배포: YAML로 원하는 상태 정의
- 자체 복구: 장애 컨테이너 재시작
- 롤링 업데이트: 무중단 배포
- 로드밸런싱, 자동 스케일링

### 연결 문장

```text
Docker는 실행 환경을 표준화하고,
Kubernetes는 컨테이너 운영을 자동화한다.
DevOps는 이를 CI/CD와 연결하여 빠르고 안정적인 배포 체계를 만든다.
```

## 7. 시험 직전 비교표

| 비교 | A | B | 핵심 차이 |
|---|---|---|---|
| CI vs CD | 자동 통합/테스트 | 자동 배포 준비/배포 | CI는 검증, CD는 전달 |
| Delivery vs Deployment | 배포 가능 상태 | 운영 자동 배포 | 사람 승인 여부 |
| 모니터링 vs 관측성 | 상태 감시 | 원인 추론 | “무슨 일?” vs “왜?” |
| Log vs Metric vs Trace | 기록 | 수치 | 흐름 |
| ConfigMap vs Secret | 일반 설정 | 민감 정보 | 보안 민감도 |
| Docker vs Kubernetes | 실행환경 포장 | 컨테이너 운영 | 포장 vs 운영 |
| Unit vs Integration | 작은 단위 | 서비스 연결 | 빠름 vs 실제성 |
| Canary vs A/B | 소수 배포 안정성 검증 | 두 버전 성과 비교 | 안정성 vs 성과 |
| DevOps vs SRE | 문화·자동화 | 신뢰성 엔지니어링 | 배포 흐름 vs 가용성 |

## 8. 서술형 예상 문제 답안 뼈대

### Q1. DevOps에서 테스트 자동화가 중요한 이유

```text
테스트 자동화는 코드 변경 시 오류를 빠르게 검출한다.
CI/CD는 자동 빌드·테스트·배포를 전제로 하므로,
테스트가 자동화되어야 잦은 배포에서도 품질을 유지할 수 있다.
Unit → Service → Integration → Canary로 검증 범위를 넓히면
운영 장애를 줄이고 빠른 피드백 루프를 만들 수 있다.
```

### Q2. CI/CD가 기존 수동 배포 문제를 어떻게 해결하는가

```text
기존 방식은 수동 배포, 환경 차이, 늦은 장애 발견이 문제였다.
CI/CD는 Commit 이후 Build, Test, Staging, Production 과정을 자동화하여
반복 작업과 실수를 줄인다.
또한 Docker와 Kubernetes를 함께 사용하면 환경 일관성과 무중단 배포를 확보할 수 있다.
```

### Q3. 모니터링과 관측성이 필요한 이유

```text
클라우드 네이티브 환경은 서비스가 분산되어 장애 원인 파악이 어렵다.
모니터링은 시스템 상태를 감시하고,
관측성은 Log, Metric, Trace를 통해 문제의 원인과 위치를 추론한다.
이를 통해 장애 조기 감지, 병목 분석, MTTR 감소, SLO 관리가 가능하다.
```

### Q4. 설정 관리와 IaC의 필요성

```text
설정이 코드에 포함되면 환경 변경마다 재빌드가 필요하고 보안 위험이 증가한다.
ConfigMap은 일반 설정을, Secret은 민감 정보를 분리하여 관리한다.
IaC는 인프라 구성을 코드로 관리하여 재현성, 버전 관리, 운영 일관성을 높인다.
따라서 설정 관리와 IaC는 클라우드 네이티브 운영 안정성의 핵심이다.
```

## 9. 마지막 암기 문장

```text
테스트 자동화는 CI/CD 신뢰성의 전제다.
CI는 검증, CD는 전달이다.
Delivery는 배포 가능 상태, Deployment는 운영 자동 배포다.
Docker는 환경을 포장하고, Kubernetes는 운영을 자동화한다.
모니터링은 상태를 보고, 관측성은 원인을 찾는다.
Log는 사건, Metric은 수치, Trace는 흐름이다.
ConfigMap은 일반 설정, Secret은 민감 정보다.
IaC는 인프라를 코드로 관리해 재현성과 일관성을 높인다.
DevOps는 빠른 배포와 협업, SRE는 신뢰성과 가용성에 초점을 둔다.
서술형은 항상 문제 → 해결 → 효과 → 연결 개념으로 쓴다.
```
