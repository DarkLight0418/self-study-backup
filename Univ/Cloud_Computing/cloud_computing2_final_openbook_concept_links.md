## 0. 서술형 답안 만능 프레임

서술형 문제는 보통 `정의만 쓰는 문제`가 아니라, **왜 필요한지 → 어떤 문제가 있는지 → 어떻게 해결하는지**를 묻는 방식으로 나올 가능성이 높습니다.

```text
[정의]
A는 ~하기 위한 개념/방법/도구이다.

[등장 배경/문제]
기존 방식에서는 ~ 문제가 발생한다.

[특징]
A는 ~, ~, ~의 특징을 가진다.

[장점]
이를 통해 ~을 개선할 수 있다.

[단점/주의]
다만 ~ 문제가 생길 수 있다.

[해결안/연결 개념]
따라서 ~와 함께 사용하거나, ~ 방식으로 보완한다.

[예시]
예를 들어 ~ 상황에서는 ~를 적용한다.
```

### 답안 연결 키워드

| 문제 유형 | 답안에 넣을 연결 구조 |
|---|---|
| 개념 설명형 | 정의 → 특징 → 장점 → 주의점 |
| 문제점 도출형 | 기존 문제 → 원인 → 영향 → 해결안 |
| 해결안 제시형 | 요구사항 → 적용 기술 → 기대효과 → 한계 |
| 비교형 | 목적 / 장점 / 단점 / 적합 상황 비교 |
| 설계형 | 장애 가정 → 자동화 → 모니터링 → 복구 전략 |

## 1. 1장 손글씨용 핵심 배치안

아래 부분은 실제로 1장에 옮겨 적을 때 우선순위가 높은 내용입니다. 자세한 설명은 뒤의 개념 카드에서 확인하면 됩니다.

### 1-1. DevOps 큰 흐름

```text
DevOps = 빠르고 안정적이며 반복 가능한 전달을 위한 문화 + 프로세스 + 도구
등장 배경 = 개발/운영 단절, 수동 배포, 환경 불일치, 긴 릴리스 주기
핵심 = CALMS + CI/CD + IaC + Monitoring + Container/K8s

기획/요구 → 코드 작성 → 빌드 → 테스트 → 배포 → 운영 → 모니터링 → 피드백
```

| 개념 | 핵심 | 문제점 | 해결 방향 |
|---|---|---|---|
| DevOps | 개발·운영 협업 방식 | 팀 이름/도구로 오해 | 문화+자동화+측정+공유 |
| CALMS | Culture, Automation, Lean, Measurement, Sharing | 자동화만 강조하면 실패 | 사람·프로세스·도구 균형 |
| CI | 자주 통합·빌드·테스트 | 늦게 통합하면 오류 누적 | 자동 빌드/테스트 |
| CD | 배포 가능 상태 또는 자동 배포 | 수동 배포·릴리스 위험 | 점진 배포·모니터링 |
| IaC | 인프라를 코드로 관리 | 수동 설정 오류 | 재현성·버전관리 |
| Observability | 왜/어디서/어떻게 문제인지 추적 | 단순 장애 감지만으로 원인 파악 어려움 | 로그+메트릭+트레이싱 |

### 1-2. 테스트와 CI/CD 흐름

```text
소스코드 → 빌드 → 테스트 → 배포 → 출시 → 출시 후
          CI 영역              CD 영역

배포 = 새 버전을 환경에 올림
출시 = 실제 트래픽을 새 버전으로 보냄
```

| 테스트 | 목적 | 특징 |
|---|---|---|
| Unit | 메서드/클래스 검증 | 빠름, 머지 전 |
| Service | 서비스/컴포넌트 검증 | Mock 사용 가능 |
| Integration | 서비스 간 상호작용 | 느리지만 중요 |
| Canary | 일부 사용자로 검증 | 운영 중 점진 평가 |
| A/B | 두 버전 비교 | 메트릭 기반 선택 |
| Chaos | 장애를 일부러 발생 | 회복력 검증 |
| Security | 취약점·권한 확인 | 자동+수동 침투 테스트 |
| Smoke | 핵심 기능 빠른 확인 | 배포 직후 유용 |

### 1-3. 모니터링·설정·보안

| 개념 | 정의 | 장점 | 주의/문제 |
|---|---|---|---|
| Monitoring | 전체 시스템 상태 확인 | 장애 감지 | 원인 분석은 부족할 수 있음 |
| Observability | 내부 상태를 외부 출력으로 추론 | 원인 추적 | 로그/메트릭/트레이싱 설계 필요 |
| Metric | 수치 기반 상태 | 출시/롤백 판단 | 이름·태그 설계 필요 |
| Log | 사건 기록 | 문제 원인 추적 | 개인정보 저장 금지 |
| Trace | 요청 흐름 추적 | 분산 시스템 병목 분석 | CID/Span 설계 필요 |
| ConfigMap | 일반 설정 분리 | 코드 재빌드 감소 | 민감정보 저장 금지 |
| Secret | 비밀정보 분리 | 보안성 향상 | 환경변수 로깅 금지, 파일 권장 |
| RBAC | 역할 기반 접근 제어 | 최소 권한 | 권한 과다 부여 주의 |

### 1-4. 클라우드 네이티브 문제 해결 패턴

| 문제 | 해결 개념 | 답안 포인트 |
|---|---|---|
| 모놀리스가 커져 배포 느림 | Strangler Pattern | 새 서비스로 점진 이전 |
| 기존 시스템과 새 서비스 충돌 | Anticorruption Layer | 프로토콜/스키마 변환 |
| 일시적 장애 | Retry + Exponential Backoff | 무제한 재시도 금지 |
| 지속 장애 확산 | Circuit Breaker | 실패 임계치 후 차단 |
| 일부 장애가 전체로 번짐 | Bulkhead | 독립 그룹으로 장애 격리 |
| 트래픽 급증 | Auto Scaling + Queue | 부하 완화, 확장 |
| DB 병목 | Cache + Partitioning + Replication | 읽기/쓰기 요구에 맞게 분리 |
| 서비스 간 과도한 호출 | Async + Queue/Stream + Batch | 결합도·부하 감소 |
| 큰 메시지 전달 | Claim-check Pattern | 메시지는 참조만, 본문은 저장소 |
| 컨테이너 보안 위험 | Verified Image + Scan + No Secret | 이미지 최소화·취약점 검사 |

## 2. 손필기 판독 반영 키워드

교안 옆 손필기에서 반복적으로 보이는 방향은 다음과 같습니다.

- DevOps는 **소프트웨어 생명주기 전체**와 연결됨.
  - 요구/기획 → 설계/구현 → 테스트 → 배포 → 운영/피드백
- 핵심은 단순 도구가 아니라 **협업 문화**.
  - `긴밀한 협업 문화`, `공유 책임`, `사람 중심`
- CALMS에서 Culture는 협업과 고객 만족/충성도와 연결 가능.
  - 장애는 개인 책임보다 **시스템 개선 기회**로 해석
- Measurement는 로그/메트릭/트레이싱으로 연결.
  - 감으로 판단하지 않고 데이터 기반으로 병목·장애를 찾음
- CI/CD는 `CI = 통합`, `CD = 배포/출시 흐름`으로 구분.
- Delivery와 Deployment는 다름.
  - Delivery = 배포 가능한 상태 유지
  - Deployment = 운영 환경까지 자동 배포
- 배포와 출시는 다름.
  - 배포 = 환경에 올림
  - 출시 = 실제 트래픽을 보냄
- 관측성은 CI/CD 성공 조건.
  - 메트릭으로 출시 지속/롤백 판단
- 설정 관리는 코드와 설정을 분리하는 것.
  - URI, DB 이름, 계정, 패스워드, Timeout, Port 등
- Secret은 환경변수로 쓸 수 있으나 로깅 위험이 있어 파일 사용이 더 안전.
- 회복력은 가용성과 복원력을 함께 고려.
  - retry, circuit breaker, graceful degradation, bulkhead
- 스케일아웃을 위해 상태 없는 서비스가 중요.
- 보안은 HTTPS/TLS, 암호화, RBAC, 최소 권한, 파드 격리와 연결.
- 서비스 메시, 모니터링, 트레이싱, 프록시/게이트웨이 개념이 서비스 간 통신과 연결됨.

# 3. 개념 카드: DevOps와 운영 자동화

## 3-1. DevOps

| 항목 | 정리 |
|---|---|
| 정의 | 소프트웨어를 더 빠르고 안정적이며 반복 가능하게 전달하기 위한 문화, 방법론, 기술의 총합 |
| 등장 배경 | 개발팀과 운영팀 단절, 수동 배포, 환경 불일치, 장애 사후 대응, 긴 릴리스 주기 |
| 특징 | 공동 책임, 자동화, 측정, 공유, 피드백 루프 |
| 장점 | 배포 속도 향상, 품질 향상, 오류 감소, 협업 강화, 평균 복구 시간 단축 |
| 단점/오해 | DevOps 팀만 만들면 된다고 오해, 도구만 도입하면 된다고 오해, 운영을 개발자에게 떠넘긴다고 오해 |
| 해결안 | 문화와 프로세스를 먼저 정리하고 CI/CD, IaC, 모니터링 도구를 결합 |

### 서술형 답안 예시

```text
DevOps는 개발과 운영을 단순히 합친 조직명이 아니라, 소프트웨어를 빠르고 안정적으로 반복 전달하기 위한 문화와 자동화 방법론이다. 전통적인 방식에서는 개발 환경과 운영 환경이 달라 “내 PC에서는 된다” 문제가 발생하고, 수동 배포와 사후 장애 대응으로 릴리스가 느려진다. DevOps는 CI/CD, IaC, 모니터링을 통해 빌드·테스트·배포를 자동화하고, 로그와 메트릭을 공유하여 빠른 피드백 루프를 만든다. 다만 도구만 도입한다고 성공하는 것은 아니며, 공동 책임 문화와 프로세스 개선이 함께 필요하다.
```

## 3-2. CALMS

| 요소 | 의미 | 장점 | 주의점 |
|---|---|---|---|
| Culture | 개발자와 운영자가 같은 목표 공유 | 책임 전가 감소, 협업 강화 | 문화 없이 도구만 쓰면 실패 |
| Automation | CI/CD, IaC, 테스트 자동화 | 반복 작업 감소, 일관성 향상 | 잘못된 자동화는 오류를 빠르게 전파 |
| Lean | 작은 변경, 낭비 제거 | 빠른 배포와 피드백 | 승인 절차를 무조건 없애면 위험 |
| Measurement | 배포 빈도, MTTR, 실패율, 메트릭 | 병목과 장애 원인 파악 | 지표만 보고 맥락을 놓치면 안 됨 |
| Sharing | 로그, 지표, 포스트모템 공유 | 조직 학습, 재발 방지 | 책임 추궁식 공유는 역효과 |

### 연결 포인트

```text
CALMS = DevOps 성숙도를 보는 기준
Culture가 기반이고, Automation은 실행 수단, Measurement는 판단 근거, Sharing은 개선 루프이다.
```

## 3-3. CI/CD

| 구분 | CI | CD |
|---|---|---|
| 풀네임 | Continuous Integration | Continuous Delivery / Deployment |
| 핵심 | 지속적 통합 | 지속적 배포 |
| 시점 | 코드 변경 후 빌드·테스트·통합 | 테스트된 결과를 환경에 배포/출시 |
| 산출물 | 바이너리, 컨테이너 이미지, 압축 파일 | 스테이징/운영 배포, 트래픽 전환 |
| 장점 | 오류 조기 발견 | 배포 위험 감소, 빠른 출시 |
| 문제점 | 테스트 품질이 낮으면 신뢰 불가 | 모니터링 없으면 장애 확산 가능 |
| 보완 | 자동 테스트, 린트, 정적 분석 | 카나리, 블루/그린, 롤백, 관측성 |

### CI/CD 파이프라인 단계

```text
소스 코드 커밋
→ 자동 빌드
→ 자동 테스트
→ 코드 품질 검사
→ 배포 준비
→ 프로덕션 배포
→ 출시/모니터링
```

### Delivery vs Deployment

| 구분 | 의미 | 시험 포인트 |
|---|---|---|
| Continuous Delivery | 언제든 배포 가능한 상태 유지 | 최종 운영 배포에는 승인/수동 단계 가능 |
| Continuous Deployment | 운영 환경까지 자동 배포 | 코드 통과 후 자동으로 운영 반영 |

### 배포 vs 출시

| 구분 | 의미 | 예시 |
|---|---|---|
| 배포 | 새 버전을 환경에 올려둠 | 컨테이너 이미지 배포, 서비스 메시 설정 |
| 출시 | 실제 트래픽을 새 버전으로 보냄 | 5% → 30% → 100% 트래픽 전환 |

### 서술형 연결

```text
CI/CD의 핵심은 변경을 작게 유지하고, 빌드·테스트·배포를 자동화하여 오류를 조기에 발견하는 것이다. 그러나 자동화된 배포는 장애도 빠르게 전파할 수 있으므로, 카나리 배포와 모니터링을 통해 새 버전의 에러율·지연·자원 사용률을 관찰하고 필요하면 롤백해야 한다.
```

## 3-4. IaC

| 항목 | 정리 |
|---|---|
| 정의 | 서버, 네트워크, 보안 설정 등 인프라를 코드로 정의하고 관리하는 방식 |
| 장점 | 환경 재현 가능, 설정 실수 감소, 버전 관리 가능, 변경 추적 용이 |
| 단점/주의 | 코드가 잘못되면 잘못된 인프라가 반복 생성될 수 있음 |
| 해결안 | 코드 리뷰, 테스트 환경 적용, 버전 관리, 자동 검증 |
| 도구 | Terraform, Ansible, AWS CloudFormation |

### 답안 포인트

```text
IaC는 운영자의 수동 설정을 줄여 환경 차이를 줄이고 재현성을 높인다. 특히 DevOps에서 CI/CD와 결합하면 애플리케이션뿐 아니라 인프라까지 일관되게 배포할 수 있다.
```

## 3-5. Docker와 Kubernetes

| 구분 | Docker | Kubernetes |
|---|---|---|
| 핵심 역할 | 애플리케이션과 실행 환경을 이미지로 패키징 | 컨테이너를 자동 배포·확장·복구·관리 |
| 해결 문제 | 실행 환경 차이 | 다중 서버 운영 복잡성 |
| 장점 | 어디서든 동일 환경 실행 | self-healing, rolling update, load balancing, auto scaling |
| 단점 | 단일 컨테이너 실행만으로는 대규모 운영 부족 | 설정 복잡, 학습 곡선 큼 |
| 연결 | Docker 이미지가 K8s에서 Pod로 실행됨 | DevOps 운영 자동화 핵심 |

# 4. 개념 카드: 테스팅과 개발 환경

## 4-1. 테스트 자동화

| 항목 | 정리 |
|---|---|
| 정의 | 코드 변경 시 반복적으로 검증해야 하는 테스트를 자동 실행하는 방식 |
| 필요성 | 빠른 배포와 출시를 위해 수동 검증만으로는 부족 |
| 장점 | 오류 조기 발견, 회귀 버그 방지, 배포 신뢰도 향상 |
| 단점/주의 | 테스트가 부정확하면 잘못된 안정감을 줌, 자동화 비용 발생 |
| 해결안 | 테스트 피라미드, Mock/Fake/Stub, 카나리/카오스 테스트 조합 |

## 4-2. 테스트 더블

| 구분 | 정의 | 장점 | 단점/주의 | 적합 상황 |
|---|---|---|---|---|
| Mock | 객체 간 상호작용을 검증하는 가짜 객체 | 호출 여부·방식 검증 가능 | 구현 세부에 테스트가 묶일 수 있음 | 결제 API 호출 여부 확인 |
| Fake | 실제처럼 동작하는 간단한 구현 | 실제 API 없어도 테스트 가능 | 실제 시스템과 차이 가능 | 가짜 권한관리, 가짜 DB |
| Stub | 지정된 값만 반환 | 단순하고 빠름 | 복잡한 흐름 검증 어려움 | 특정 응답값 고정 |

## 4-3. 테스트 피라미드

```text
        UI Test        ← 느림, 비용 큼, 적게
     Service Test      ← 서비스/컴포넌트 검증
  Unit Test            ← 빠름, 많게, 기본 검증
```

| 테스트 | 특징 | 장점 | 단점 |
|---|---|---|---|
| Unit | 메서드/클래스 단위 | 빠르고 자동화 쉬움 | 전체 흐름 검증 불가 |
| Service | 서비스/컴포넌트 단위 | 비즈니스 기능 검증 | Mock 설계 필요 |
| UI | 사용성·접근성·화면 흐름 | 사용자 관점 검증 | 느리고 깨지기 쉬움 |

## 4-4. 주요 테스트 유형

| 테스트 | 정의 | 장점 | 문제점/주의 | 연결 개념 |
|---|---|---|---|---|
| 성능 테스트 | 요청부터 응답까지 시간 측정 | 병목 발견 | 초기 기준값 필요 | latency, throughput |
| 부하 테스트 | 최대/피크 부하 검증 | 장애 지점 확인 | 실서비스와 다른 환경이면 부정확 | autoscaling |
| 보안/침투 테스트 | 취약점, 권한 문제 탐지 | 보안 사고 예방 | 일부 수동 테스트 필요 | DevSecOps |
| A/B 테스트 | 두 버전 성능 비교 | 데이터 기반 선택 | 트래픽 분배 필요 | metric, KPI |
| 카나리 테스트 | 일부 사용자에게만 새 버전 노출 | 위험 낮은 출시 | 고비용, 지속적 관찰 필요 | progressive delivery |
| 카오스 테스트 | 의도적으로 장애 발생 | 회복력 검증 | 운영 영향 주의 | resilience, SRE |
| 퍼지 테스트 | 무작위/예상 밖 입력 검증 | 예외 입력 발견 | 결과 분석 비용 | security testing |
| 스모크 테스트 | 핵심 기능 빠른 확인 | 배포 직후 유용 | 깊은 검증 불가 | release verification |

## 4-5. 실서비스 테스트 단계

```text
[배포 전]
- 코드 구축, 패키지, 이미지 저장
- 유닛/통합/인수 테스트

[배포]
- 실서비스 환경에 올림
- 아직 트래픽 발생 전
- 설정, 통합, 부하 테스트 확인

[출시]
- 트래픽 증가
- 모니터링과 추가 테스트

[출시 후]
- 운영
- 카오스 테스트, A/B 테스트
- 예외·장애 대응 대기
```

## 4-6. 로컬 개발 환경과 클라우드 개발 환경

# 5. 개념 카드: CI/CD 세부 운영

## 5-1. 모노리포 vs 멀티리포

| 구분 | 모노리포 | 멀티리포 |
|---|---|---|
| 정의 | 모든 서비스/함수/도구/앱을 하나의 저장소에 저장 | 각 서비스/함수/도구/앱을 여러 저장소에 분산 |
| 장점 | 공유·협업 쉬움, 의존성 재사용, 하나의 버전/태그 관리 | 서비스별 독립 배포·권한 관리 쉬움 |
| 단점 | 작은 변경에도 빌드 영향, 저장소 커짐, 빌드 장애 범위 큼 | 의존성/버전 관리 복잡, 중복 코드 가능 |
| 적합 상황 | 공통 라이브러리와 협업이 중요한 조직 | 서비스별 독립성이 큰 마이크로서비스 |

## 5-2. 멀티스테이지 빌드

| 항목 | 정리 |
|---|---|
| 정의 | 빌드 단계와 실행 단계를 분리하여 최종 이미지에는 실행에 필요한 산출물만 복사 |
| 장점 | 이미지 크기 감소, 보안 표면 감소, 배포 속도 개선 |
| 문제점 | Dockerfile 설계 필요 |
| 서술형 포인트 | 컨테이너 이미지를 작게 유지하는 CI/CD 최적화 전략 |

## 5-3. CI/CD 파이프라인 유의 사항

- 모노리포/멀티리포 모두 빌드가 빨라야 함.
- 테스트 신뢰성이 확보되어야 함.
- 컨테이너 이미지는 가능한 한 작게 유지.
- 트래픽 전환 전략을 결정해야 함.
  - 전체 트래픽
  - 일부 트래픽
  - 특정 조건 기반
- 관측 가능한 서비스가 성공적인 CI/CD 파이프라인의 핵심.

# 6. 개념 카드: 모니터링과 관측성

## 6-1. Monitoring vs Observability

| 구분 | Monitoring | Observability |
|---|---|---|
| 핵심 질문 | 지금 문제가 발생했는가? | 왜, 어디서, 어떻게 문제가 발생했는가? |
| 대상 | 메트릭 중심, 전체 시스템 상태 | 로그, 메트릭, 트레이싱, 예외 메시지 |
| 장점 | 장애 감지와 알림 | 원인 분석과 디버깅 |
| 단점 | 원인 설명이 부족할 수 있음 | 설계와 데이터 수집 비용 필요 |
| 도구 | Grafana, Prometheus | Jaeger, OpenTracing, ELK |

### 서술형 답안 예시

```text
모니터링은 시스템이 정상인지 확인하는 활동이고, 관측성은 문제가 발생했을 때 내부 상태를 로그, 메트릭, 트레이싱 같은 외부 출력으로 추론하는 능력이다. 클라우드 네이티브 환경은 서비스가 분산되어 있어 단순히 장애 발생 여부만으로는 원인을 찾기 어렵다. 따라서 에러율, 지연, 자원 이용률 같은 메트릭과 요청 흐름을 추적하는 트레이싱, 구조화된 로그를 함께 수집해야 한다.
```

## 6-2. 핵심 메트릭

| 메트릭 | 의미 | 활용 |
|---|---|---|
| Error Rate | 요청 실패율, HTTP 500 수 | 출시 계속/롤백 판단 |
| Request Rate | 초당 HTTP 요청, DB 트랜잭션 | 트래픽 증가 확인 |
| Latency | 요청 처리 시간 | 성능 저하 탐지 |
| Utilization | CPU, 메모리, 디스크 사용률 | 자원 병목 확인 |

## 6-3. Prometheus 메트릭 타입

| 타입 | 의미 | 예시 |
|---|---|---|
| Counter | 증가만 하는 값 | 요청 수, 에러 수, 재시작 수 |
| Gauge | 증가/감소하는 값 | CPU 사용량, 메모리 사용량, 프로세스 수 |
| Histogram | 관측값을 버킷으로 분류 | 요청 지속 시간, 응답 크기 |
| Summary | Histogram과 유사한 요약 통계 | 지연 시간 분위수 |

## 6-4. 로깅 고려 사항

| 항목 | 이유 |
|---|---|
| 구조화된 로깅 | 도구와 자동화가 파싱 가능 |
| 명확·간결한 로그 | 사람이 원인 파악 가능 |
| 동일 시간대/형식 | 분산 시스템 시간 비교 가능 |
| 카테고리 분류 | debug, info, error 구분 |
| 개인정보/민감정보 배제 | 보안 사고 방지 |
| 중앙 집중 수집 | 한 곳에서 검색·분석 가능 |
| 요청 ID/CID | 서비스 간 요청 추적 가능 |

## 6-5. 분산 추적

| 항목 | 정리 |
|---|---|
| 정의 | 분산 시스템에서 하나의 요청이 여러 서비스로 이동하는 흐름을 추적 |
| 목적 | 장애와 성능 저하 원인 분석 |
| 핵심 단위 | Span: 이름, 시작/끝 시간, 태그, 로그, 컨텍스트, 다른 Span 참조 |
| 도구 | Jaeger, OpenTracing |
| 장점 | 어느 서비스에서 병목이 발생했는지 확인 가능 |

## 6-6. Health / Liveness / Readiness

| 구분 | 의미 | 사용 목적 |
|---|---|---|
| Health | 서비스가 건강한지 확인 | 기본 상태 확인 |
| Liveness | 컨테이너가 살아있는지 확인 | 비정상 컨테이너 재시작 판단 |
| Readiness | 요청 받을 준비가 되었는지 확인 | 준비 전 트래픽 유입 방지 |

# 7. 개념 카드: 설정 관리

## 7-1. 설정 관리

| 항목 | 정리 |
|---|---|
| 정의 | 서비스/함수가 실행될 때 필요한 정보를 코드와 분리하여 관리하는 방식 |
| 대상 | DB/큐/메시징 연결 문자열, 인증정보, API 키, 인증서, timeout, port, 서비스 이름 |
| 장점 | 코드 재빌드 없이 환경별 설정 변경, 여러 환경 구성 쉬움 |
| 문제점 | 민감정보 노출, 환경변수 로깅 위험 |
| 해결안 | ConfigMap과 Secret 분리, 민감정보는 Secret/관리형 보안 저장소 사용 |

## 7-2. ConfigMap

| 항목 | 정리 |
|---|---|
| 정의 | Kubernetes에서 일반 설정값을 저장하는 자원 |
| 데이터 소스 | 디렉터리, 파일, 리터럴 값 |
| 사용 방식 | 단일 환경 변수, 다중 환경 변수, 볼륨 마운트 |
| 장점 | 설정 변경 시 코드 수정 최소화, 환경별 구성 쉬움 |
| 주의 | 비밀번호/API 키 저장 금지 |

## 7-3. Secret

| 항목 | 정리 |
|---|---|
| 정의 | 비밀번호, API 키, 인증서 같은 민감정보를 저장하는 전용 자원 |
| 특징 | Base64 인코딩 값 저장, 파드에 환경변수 또는 파일로 마운트 가능 |
| 장점 | 비밀정보를 코드/이미지/파드 내부에 직접 저장하지 않음 |
| 주의 | 환경변수는 로깅 위험이 있으므로 가능하면 파일로 사용 |
| 보완 | 클라우드 공급자의 관리형 보안 저장소 사용 |

## 7-4. Helm / Chart / CNAB

| 개념 | 정리 |
|---|---|
| Helm | Kubernetes 자원 파일을 템플릿화하여 설치/업그레이드하는 도구 |
| Chart | Kubernetes 자원 파일을 패키징한 단위 |
| CNAB | 복잡한 클라우드 네이티브 애플리케이션 패키징 방식 |

# 8. 개념 카드: 클라우드 네이티브로 이동하기

## 8-1. 클라우드 네이티브 재설계가 필요한 경우

- 코드베이스가 커져 업데이트 출시가 오래 걸림.
- 구성 요소별 요구 규모가 다름.
  - 프런트엔드, 비즈니스, 데이터 계층을 독립적으로 확장하고 싶음.
- 새롭고 좋은 기술을 부분적으로 도입하고 싶음.
- 단순히 클라우드로 옮기기만 한다면 IaaS 사용에 가까움.
- 클라우드의 장점을 살리려면 애플리케이션 구조 자체를 재설계해야 함.

## 8-2. 단순 서비스 먼저 분리

| 항목 | 정리 |
|---|---|
| 정의 | 간단하고 의존성이 적은 기능부터 모놀리스에서 분리 |
| 장점 | 위험을 낮추고 운영 경험을 작게 쌓을 수 있음 |
| 문제점 | 핵심 도메인 분리 전까지 효과가 제한적일 수 있음 |
| 연결 | 작은 인프라, CI/CD 파이프라인, 자동화 설정 학습 |

## 8-3. Anticorruption Layer

| 항목 | 정리 |
|---|---|
| 정의 | 기존 모놀리스와 신규 서비스 사이에 두는 파사드/어댑터 계층 |
| 역할 | 프로토콜, 스키마, 요청/응답 형식 변환 |
| 장점 | 새 시스템이 기존 시스템 구조에 오염되는 것을 방지 |
| 단점 | 중간 계층이 추가되어 복잡도 증가 |
| 적합 상황 | 기존 시스템과 신규 마이크로서비스를 병행 운영할 때 |

```text
[모놀리스] ↔ [손상 방지 레이어] ↔ [신규 서비스들]
            요청/응답 변환
            프로토콜/스키마 변환
```

## 8-4. Strangler Pattern

| 항목 | 정리 |
|---|---|
| 정의 | 모놀리스를 한 번에 제거하지 않고, 기능별로 새 서비스/함수로 점진 이전하는 패턴 |
| 방식 | 게이트웨이/파사드가 요청을 기존 모놀리스 또는 신규 서비스로 라우팅 |
| 장점 | 대규모 재작성 위험 감소, 단계적 전환 가능 |
| 단점 | 전환 기간 동안 기존/신규 시스템 공존 복잡도 |
| 연결 | 데이터 마이그레이션, ACL, API Gateway |

```text
1단계: 요청 → 모놀리스
2단계: 일부 요청 → 신규 서비스, 나머지 → 모놀리스
3단계: 대부분 요청 → 신규 서비스
4단계: 기존 모놀리스 제거
```

## 8-5. 데이터 마이그레이션 전략

| 문제 | 해결 방향 |
|---|---|
| 중앙 공유 데이터스토어 | 신규 데이터스토어와 기존 데이터스토어를 공존시킨 뒤 점진 제거 |
| 기존 코드의 강한 결합 | 기존 코드 수정보다 새 서비스에 맞게 재작성 |
| 기존 기술의 한계 | 서비스 목적에 맞는 언어, 프레임워크, 데이터 구조 선택 |
| 모놀리스 제거 시점 | 새 서비스로 트래픽 리디렉트 후 제거 |

# 9. 개념 카드: 회복력 확인

## 9-1. 회복력

| 항목 | 정리 |
|---|---|
| 정의 | 장애 발생 시 다운타임과 데이터 유실을 피하거나 줄이는 대응 능력 |
| 전제 | 장애는 발생하지 않는 것이 아니라, 발생한다고 가정하고 설계 |
| 장점 | 서비스 지속성, 사용자 경험 보호 |
| 연결 | retry, circuit breaker, graceful degradation, bulkhead, health/readiness check |

## 9-2. Retry 전략

| 전략 | 의미 | 장점 | 단점/주의 |
|---|---|---|---|
| Constant | 매번 같은 시간 대기 후 재시도 | 단순 | 동시에 몰리면 부하 증가 |
| Linear | 대기 시간을 일정하게 증가 | 부하 완화 | 장애가 길면 여전히 부담 |
| Exponential Backoff | 대기 시간을 지수적으로 증가 | 장애 시스템 보호 | 너무 길면 사용자 대기 증가 |

### Retry 주의점

- 무제한 재시도는 시스템 부하를 키움.
- 일시적 장애에만 재시도해야 함.
- 재시도 실패나 일시적이지 않은 실패는 요청을 취소해야 함.

## 9-3. Circuit Breaker

| 항목 | 정리 |
|---|---|
| 정의 | 실패가 일정 횟수를 넘으면 일정 시간 동안 요청을 차단하고 에러를 반환하는 패턴 |
| 장점 | 장애 전파 방지, 전체 시스템 보호 |
| 단점 | 임계값 설정이 부정확하면 정상 요청도 차단 가능 |
| 연결 | retry 실패 후 circuit breaker 적용 |

## 9-4. Graceful Degradation

| 항목 | 정리 |
|---|---|
| 정의 | 일부 기능 장애 시에도 사용자가 이해할 수 있는 수준의 경험을 제공하는 방식 |
| 예시 | 데이터 검색 불능 시 캐시 데이터 표시, 복구 후 최신 데이터 표시 |
| 장점 | 완전 장애보다 사용자 경험 유지 |
| 단점 | 최신성/정확성 저하 가능 |

## 9-5. Bulkhead Pattern

| 항목 | 정리 |
|---|---|
| 정의 | 시스템을 독립된 그룹으로 분리해 한 부분의 장애가 전체로 번지지 않게 하는 패턴 |
| 장점 | 장애 격리, 안정성 향상 |
| 단점 | 리소스 분리와 운영 복잡도 증가 |
| 비유 | 배의 격벽처럼 한 구역 침수 시 전체 침몰 방지 |

## 9-6. Rate Limiting vs Throttling

| 구분 | 의미 | 방향 |
|---|---|---|
| Rate Limiting | 서비스로 들어오는 요청 개수 제한 | Inbound 보호 |
| Throttling | 서비스에서 나가는 요청 개수 제한 | Outbound 제어 |

# 12. 개념 카드: 함수와 서버리스 운영

## 12-1. 함수 설계 원칙

| 원칙 | 이유 |
|---|---|
| 단일 목적 | 단일 책임 원칙, 파악·테스트·디버깅 쉬움 |

| 실행 시간 줄이기 | FaaS 실행 시간 제한 대응 |
| 큐 사용 | 함수 간 직접 호출 대신 이벤트 기반 실행 |

### 서술형 연결

```text
서버리스 함수는 실행 시간이 제한되고 상태를 내부에 저장하기 어렵기 때문에, 단일 목적의 짧은 함수로 작성해야 한다. 함수 간 직접 호출은 결합도를 높이므로 큐나 데이터스토어에 이벤트를 넣고 다른 함수가 이를 처리하도록 설계하는 것이 좋다.
```

| 항목 | 정리 |

## 15-3. 동기 vs 비동기 통신

| 구분 | 동기 통신 | 비동기 통신 |
|---|---|---|

| 단점 | 지연·장애 전파 가능 | 최종 일관성, 흐름 추적 필요 |
| 적합 | 즉시 응답이 필요한 API | 트래픽 스파이크, 백그라운드 처리 |

## 15-4. 직렬화

| 방식 | 장점 | 단점 |
|---|---|---|
| JSON | 가독성, 독립성, 확장성 | 메모리 사용량 큼, 메시지 크기 큼 |
| Protocol Buffer | 작은 페이로드, 빠른 전송, 구조화 | proto 파일과 코드 생성 필요 |

## 15-5. Queue / Stream / Batch / Claim-check

| 개념 | 정리 |
|---|---|
| Queue/Stream | 메시지를 버퍼처럼 저장하여 서비스 처리 능력에 맞게 소비 |
| Batch | 여러 요청을 한 번에 처리하여 I/O 비용 절감 |
| Claim-check | 큰 메시지는 저장소에 두고 메시지에는 참조만 전달 |

# 17. 서술형 예상 문제별 답안 뼈대

## 17-1. DevOps가 등장한 이유와 해결 방안을 설명하라

```text
전통적인 개발·운영 방식에서는 개발 환경과 운영 환경이 달라 오류가 발생하고, 수동 배포와 사후 장애 대응으로 릴리스 주기가 길어진다. DevOps는 개발과 운영의 장벽을 낮추고 공동 책임 문화를 형성하며, CI/CD로 빌드·테스트·배포를 자동화하고 IaC로 인프라 설정을 코드화한다. 또한 모니터링과 관측성을 통해 장애 원인을 빠르게 파악하고 피드백을 반복한다. 따라서 DevOps는 단순한 조직 이름이나 도구가 아니라, 빠르고 안정적인 소프트웨어 전달을 위한 문화와 자동화 체계이다.
```

## 17-2. CI/CD에서 관측성이 왜 중요한가

```text
CI/CD는 변경사항을 빠르게 배포할 수 있게 하지만, 잘못된 변경도 빠르게 운영 환경에 퍼질 수 있다. 따라서 새 버전 출시 후 에러율, 요청 비율, 지연, 자원 이용률을 관찰해야 한다. 로그와 트레이싱을 함께 수집하면 어느 서비스에서 장애나 병목이 발생했는지 파악할 수 있다. 이 정보를 바탕으로 카나리 배포를 계속 진행할지, 롤백할지 결정한다. 즉 관측성은 자동 배포의 위험을 제어하는 안전장치이다.
```

## 17-3. 모놀리스를 클라우드 네이티브로 전환하는 전략을 설명하라

```text
모놀리스를 한 번에 마이크로서비스로 전환하면 위험이 크므로, 의존성이 적고 단순한 서비스부터 분리한다. 기존 시스템과 신규 서비스 사이에는 손상 방지 레이어를 두어 프로토콜과 스키마 차이를 변환하고, 스트랭글러 패턴을 사용해 게이트웨이가 요청을 기존 모놀리스 또는 신규 서비스로 점진적으로 라우팅하게 한다. 데이터는 중앙 공유 데이터스토어를 분해하되, 신규 데이터스토어와 기존 데이터스토어를 일정 기간 공존시킨 뒤 기존 저장소를 제거한다. 이를 통해 배포 위험을 줄이고 클라우드 네이티브 운영 경험을 축적할 수 있다.
```

## 17-4. 장애에 대비한 회복력 설계 방안을 설명하라

```text
클라우드 네이티브 시스템은 장애가 발생하지 않는다고 가정하지 않고, 장애가 발생해도 전체 서비스가 무너지지 않도록 설계한다. 일시적인 실패에는 재시도를 적용하되 무제한 재시도를 금지하고 지수 백오프를 사용한다. 지속적인 실패에는 서킷 브레이커를 적용해 요청을 차단하고 장애 확산을 막는다. 또한 우아한 성능 저하로 캐시 데이터를 제공하거나 일부 기능만 제한하고, 벌크헤드 패턴으로 장애 영역을 격리한다. Kubernetes에서는 liveness/readiness probe와 CPU/메모리 제한을 통해 자동 복구와 자원 관리를 수행한다.
```

## 17-5. 설정 관리와 비밀정보 관리의 차이를 설명하라

```text
설정 관리는 서비스 실행에 필요한 포트, 타임아웃, DB 연결 문자열 같은 값을 코드와 분리하는 것이다. Kubernetes에서는 일반 설정은 ConfigMap으로 관리하고, 비밀번호, API 키, 인증서 같은 민감정보는 Secret으로 관리한다. ConfigMap은 환경별 설정을 쉽게 바꿀 수 있게 하지만 민감정보 저장에는 적합하지 않다. Secret은 비밀정보를 파드에 환경변수나 파일로 제공할 수 있으나, 환경변수는 로그로 노출될 수 있으므로 가능하면 파일 마운트나 클라우드 관리형 보안 저장소를 사용하는 것이 안전하다.
```

## 17-6. 서비스 확장성 문제와 해결 방안을 설명하라

```text
확장성은 성능을 크게 떨어뜨리지 않고 증가한 부하를 처리할 수 있는 능력이다. 클라우드 네이티브 서비스는 인스턴스 내부에 상태를 저장하지 않는 stateless 구조로 설계해야 수평 확장이 쉽다. Kubernetes의 HPA는 CPU, 메모리, 커스텀 메트릭을 기준으로 파드 수를 늘리고, 클러스터 오토스케일링은 파드 배치가 불가능할 때 노드 수를 늘린다. 또한 자주 사용하는 데이터는 캐시하고, 서비스 한계를 넘는 작업은 파티셔닝해 여러 인스턴스에 나눠 처리한다. 단, 캐시는 최신성 문제, 파티셔닝은 데이터 분산 기준 문제가 있으므로 요구사항에 맞게 설계해야 한다.
```

## 17-7. 서비스 간 통신 문제와 해결 방안을 설명하라

```text
마이크로서비스에서는 서비스가 분산되어 있어 동기 호출이 많아지면 지연과 장애 전파가 발생할 수 있다. 이를 줄이기 위해 비동기 통신을 선호하고, 큐나 스트림을 사용해 요청을 버퍼링한다. 트래픽이 급증해도 메시지를 저장해두고 서비스 처리 능력에 맞게 소비할 수 있어 가용성과 확장성이 향상된다. 또한 여러 요청은 배치 처리해 I/O 비용을 줄이고, 큰 메시지는 claim-check 패턴을 사용해 저장소에 본문을 두고 메시지에는 참조만 전달한다. 데이터 직렬화는 JSON보다 Protocol Buffer를 사용하면 페이로드와 처리 비용을 줄일 수 있다.
```

## 17-8. 컨테이너 운영 보안과 관리 방안을 설명하라

```text
컨테이너 이미지는 신뢰할 수 있는 저장소에 저장하고 검증된 이미지를 사용해야 한다. 이미지에는 명시적인 태그를 붙여 코드 버전과 연결하고, 작은 베이스 이미지에서 시작해 운영에 필요한 파일만 포함해야 한다. privileged 모드는 호스트 접근 권한을 크게 열어 보안 위험이 있으므로 피하고, 이미지 내부에 비밀정보나 설정을 저장해서는 안 된다. 비밀정보는 Secret 또는 관리형 보안 저장소로 분리하고, 데이터는 컨테이너 내부가 아니라 볼륨에 저장한다. 또한 취약점 스캔 도구로 이미지를 검사하고 발견된 취약점은 패치 후 재빌드해야 한다.
```

# 18. 마지막 비교 정리

| 비교 | A | B | 핵심 차이 |
|---|---|---|---|
| DevOps vs SRE | 문화·철학, 협업·자동화 | 신뢰성·가용성 엔지니어링 | DevOps는 방식, SRE는 신뢰성 역할 |
| CI vs CD | 빌드·테스트·통합 | 배포·출시 | CI는 통합, CD는 전달 |
| Delivery vs Deployment | 배포 가능 상태 | 운영 자동 배포 | 자동 운영 반영 여부 |
| 배포 vs 출시 | 환경에 올림 | 트래픽 연결 | 사용자가 실제로 쓰는 시점 차이 |
| Monitoring vs Observability | 상태 감지 | 원인 추론 | 무엇이 문제인가 vs 왜 문제인가 |
| ConfigMap vs Secret | 일반 설정 | 민감정보 | 보안 요구 차이 |
| Liveness vs Readiness | 살아있는가 | 요청 받을 준비가 되었는가 | 재시작 판단 vs 트래픽 유입 판단 |
| Rate limiting vs Throttling | 들어오는 요청 제한 | 나가는 요청 제한 | Inbound vs Outbound |
| Retry vs Circuit Breaker | 다시 시도 | 일정 실패 후 차단 | 일시 장애 대응 vs 장애 확산 차단 |
| Graceful degradation vs Bulkhead | 기능 저하로 경험 유지 | 장애 영역 격리 | 사용자 경험 보호 vs 시스템 보호 |
| Monorepo vs Multirepo | 한 저장소 | 여러 저장소 | 공유 편의성 vs 서비스 독립성 |
| JSON vs Protobuf | 가독성 좋음 | 빠르고 작음 | 사람 친화 vs 성능 친화 |
| 동기 통신 vs 비동기 통신 | 즉시 응답 | 큐/이벤트 기반 처리 | 단순성 vs 결합도 완화 |
| Scale-up vs Scale-out | 한 서버 성능 증가 | 인스턴스 수 증가 | 수직 확장 vs 수평 확장 |
| Stateless vs Stateful | 내부 상태 없음 | 내부 상태 유지 | 확장 용이성 차이 |

# 19. 시험 직전 체크리스트

- [ ] DevOps를 `문화 + 프로세스 + 도구`로 설명할 수 있다.
- [ ] CALMS 다섯 요소를 각각 문제 해결 관점으로 설명할 수 있다.
- [ ] CI/CD, Delivery/Deployment, 배포/출시 차이를 구분할 수 있다.
- [ ] 테스트 더블 Mock/Fake/Stub 차이를 예시로 설명할 수 있다.
- [ ] 테스트 피라미드와 테스트 실행 시점을 연결할 수 있다.
- [ ] 모니터링과 관측성의 차이를 로그/메트릭/트레이싱으로 설명할 수 있다.
- [ ] ConfigMap과 Secret의 차이와 주의점을 설명할 수 있다.
- [ ] 모놀리스 전환 시 ACL과 Strangler Pattern을 연결할 수 있다.
- [ ] Retry, Circuit Breaker, Graceful Degradation, Bulkhead를 장애 대응 흐름으로 설명할 수 있다.
- [ ] 보안 강화에서 최소 권한, RBAC, Secret, TLS, 파드 격리를 연결할 수 있다.
- [ ] 성능과 확장성 차이, Stateless, HPA, 캐시, 파티셔닝을 연결할 수 있다.
- [ ] 함수 설계 원칙을 FaaS 제약과 연결할 수 있다.
- [ ] 서비스 커뮤니케이션에서 비동기, 큐/스트림, 배치, Claim-check를 연결할 수 있다.
- [ ] 컨테이너 이미지 운영 원칙을 보안과 배포 성능 측면에서 설명할 수 있다.

# 20. 1장 손글씨 최종 추천 구조

실제 오픈북 1장에는 아래처럼 쓰면 가장 효율적입니다.

```text
[상단 20%] DevOps 전체 흐름
- DevOps 정의, CALMS, CI/CD 흐름, 배포/출시 차이

[좌측 30%] 테스트/CI-CD/모니터링
- 테스트 종류 표, CI/CD 단계, 메트릭 4종, 로그/메트릭/트레이싱

[우측 30%] 설정/보안/회복력
- ConfigMap vs Secret, RBAC/TLS/최소권한, Retry/Circuit/Bulkhead

[하단 20%] 클라우드 네이티브 전환/확장/통신/컨테이너
- ACL, Strangler, Stateless, Auto Scaling, Queue/Stream, Container 원칙
```

### 꼭 넣을 압축 문장 12개

1. DevOps = 빠르고 안정적이며 반복 가능한 전달을 위한 문화+프로세스+도구.
2. CALMS = 협업 문화, 자동화, 낭비 제거, 측정, 공유.
3. CI = 코드 변경을 자주 통합·빌드·테스트하여 오류를 조기 발견.
4. CD = 테스트된 산출물을 배포/출시하고 모니터링으로 위험 제어.
5. 배포는 환경에 올리는 것, 출시는 실제 트래픽을 보내는 것.
6. 관측성 = 로그+메트릭+트레이싱으로 장애 원인을 추적하는 능력.
7. ConfigMap은 일반 설정, Secret은 비밀번호/API 키/인증서.
8. 회복력은 장애를 가정하고 Retry, Circuit Breaker, Bulkhead로 대응.
9. ACL은 기존 시스템과 새 서비스 사이의 번역 계층.
10. Strangler는 모놀리스를 새 서비스/함수로 점진 대체하는 패턴.
11. Stateless 서비스는 스케일아웃에 유리하다.
12. 컨테이너에는 데이터와 비밀정보를 저장하지 않는다.
